# Alembic Migration History & Enterprise Tables

## The Situation
On `2026-08-11`, while working on the `master` branch to implement 2FA, we ran into an issue where Alembic attempted to drop three tables:
- `enterprise_organizations`
- `enterprise_nodes`
- `enterprise_clusters`

## Why did this happen?
1. Previously, these tables were created and migrated in the local PostgreSQL database while working on the `feature/enterprise` branch.
2. The code was later reverted and we switched back to the `master` branch, meaning the Python SQLAlchemy models for these enterprise tables no longer existed in the codebase.
3. However, the database itself (running in Docker) *still contained the tables* from the previous migration.
4. When running `alembic revision --autogenerate -m "add_2fa"` on `master`, Alembic compared the current models (which didn't have the enterprise tables) against the database (which did). It assumed the tables were meant to be deleted and automatically added `op.drop_table()` commands to the new `c3b975bf3c53_add_2fa.py` migration.

## The Fix
To prevent data loss and avoid future merge conflicts when switching back to the `feature/enterprise` branch, we **manually removed** the `op.drop_table()` and `op.create_table()` lines from the autogenerated 2FA migration file (`c3b975bf3c53_add_2fa.py`). 

The final `c3b975bf3c53_add_2fa.py` file only contains the commands to add the `totp_secret` and `is_2fa_enabled` columns.

## What to do next time
When you switch back to the `feature/enterprise` branch and merge `master` into it:
1. You will have both the 2FA migration and your original enterprise migrations.
2. Because we stripped the `drop_table` commands from the 2FA migration, there will be no conflicts.
3. You can safely run `alembic upgrade head` and the enterprise tables will remain perfectly intact alongside the new 2FA columns.
